# 설계 요약

2026-11-24 기준으로 이 저장소에 **구현된 것**의 설계다. 목표와 근거, 단계별 계획까지 담은 상세 설계안은 따로 있다: [소프트웨어 상세 설계안(초안 v0.4)](https://claude.ai/artifact/R7AHGE5GLftfDZYvz3TCKD).

테마와 새 화면 뼈대의 설계(아직 구현 전)는 [UI_DESIGN.md](UI_DESIGN.md)에 있다.

## 무엇을 만드는가

문자와 문장으로 적는 가계부다. 결제 문자를 붙여넣거나 한 줄로 적으면 기기 안에서 해석해 거래 초안을 만들고, 사용자가 확인하면 저장한다. 로그인하면 여러 기기가 같은 가계부를 본다.

| 대상 | 방식 |
| --- | --- |
| Windows, Android | Flutter 앱(같은 코드) |
| 웹, iPhone · iPad · Mac | Flutter 웹 앱(GitHub Pages) |
| Apple 네이티브 앱 | 마지막 단계 |

## 구성

```
┌──────────────── 기기(앱 · 브라우저) ─────────────────┐
│  화면(features)  ── Riverpod ──  저장소(repository)   │
│      │                               │                │
│  입력 해석(ai)                    로컬 DB(SQLite)      │
│   규칙 → (모르는 형식만) LLM         │  └ 대기열(outbox)│
│                                  동기화 엔진(sync)    │
└──────────────────────────────────────┬───────────────┘
                                       │ 로그인했을 때만
                         ┌─────────────▼─────────────┐
                         │ Supabase                  │
                         │  Auth(Google) · PostgreSQL│
                         │  sync_push · sync_pull    │
                         └───────────────────────────┘
```

- **모든 읽기와 쓰기는 로컬 DB에서 먼저 일어난다.** 서버가 없어도, 로그인하지 않아도 앱은 그대로 쓰인다.
- **원문은 기기 밖으로 나가지 않는다.** 서버에는 사용자가 확인해 저장한 거래와 설정만 올라간다.
- **AI가 읽은 것은 초안이다.** 검토 카드에서 확인해야 저장된다.

## 층

| 층 | 폴더 | 하는 일 |
| --- | --- | --- |
| 화면 | `lib/features`, `lib/app` | 화면, 화면 이동, 상태 제공(Riverpod), 앱 시작 |
| 입력 해석 | `lib/ai` | 붙여넣은 글 · 문장을 거래 초안으로 바꾼다 |
| 도메인 | `lib/domain`, `lib/core` | 날짜, 월 기간, 집계, 열거형, 형식 |
| 데이터 | `lib/data` | 로컬 DB, 저장소, 동기화, 서버 연결 |
| 서버 | `supabase/` | 테이블, 행 단위 보안, 동기화 함수 |

화면은 저장소와 제공자만 본다. 저장소는 DB에 쓰면서 같은 트랜잭션에서 대기열에 올린다. 동기화 엔진과 서버 연결은 인터페이스(`SyncGateway`, `AuthService`)로 나뉘어 있어 시험에서는 가짜로 바꿔 끼운다.

## 입력 해석

순서는 `lib/ai/input_interpreter.dart`에 있다.

1. **형식 규칙**: 아는 은행 · 카드 문자와 앱 알림(32개 형식)을 정규식으로 읽고, 안내문(예정 · 광고 · 인증번호 · 실패)을 거른다.
2. **한 줄 문장**: 사람이 쓴 문장은 규칙이 날짜 · 금액 · 방향을 읽는다.
3. **모르는 형식의 문자**: 기기 안의 소형 LLM에 넘긴다. 규칙이 날짜 · 금액 · 이름 **후보**를 뽑고 모델은 그 안에서 고르기만 한다(문법으로 강제).
4. **검토 카드**: 중복, 취소 대상, 자산 매칭, 경고를 붙여 보여 준다.

이 순서는 실측으로 정했다(`eval/README.md`). 모르는 형식의 문자에서 모든 항목이 맞은 초안은 규칙만 0/20, Qwen3.5-2B를 붙이면 13/20이었고, 한 줄 문장은 규칙이 모델보다 정확했다. 앱 안에서 모델을 돌리는 연동은 아직 없다.

## 저장

- 로컬 DB는 SQLite다(Drift). Windows · Android는 파일, 웹은 SQLite WebAssembly + 브라우저 저장소.
- 서버 테이블 9개(가계부, 프로필, 자산, 분류, 거래, 예산, 반복, 분류 규칙, 월 요약)와 같은 모양의 테이블을 기기에 두고, 기기 전용으로 대기열 · 동기화 상태 · 충돌 기록을 둔다.
- 삭제는 표시만 한다(다른 기기로 전파해야 하므로).
- 웹에서 공유 워커가 없는 브라우저는 탭마다 DB 사본을 따로 든다. 나중에 연 탭만 쓰이고 먼저 열린 탭은 멈춘다.

## 로그인과 동기화

- 서버 주소와 공개 키를 넣어 빌드해야 켜진다. 없으면 기기 안에서만 동작한다.
- 로그인은 Google(Supabase Auth, PKCE)이다. 지금은 웹에서만 된다.
- **첫 로그인**: 기기에 적어 둔 거래 · 자산 · 분류 · 월 시작일을 계정의 가계부로 옮긴다. 이름과 종류가 같은 기본 분류 · 자산은 서버 것을 쓴다. 다른 계정이 쓰던 기기에서는 섞지 않고 묻는다(`data/sync/ledger_adoption.dart`).
- **올리기**: 대기열의 변경을 묶어 `sync_push`로 보낸다. 같은 묶음을 다시 보내도 한 번만 적용된다.
- **받기**: `sync_pull`로 서버 일련번호(server_seq) 뒤의 변경을 받는다.
- **충돌**: 행 단위로 나중에 고친 쪽이 이긴다. 진 쪽은 기기에 남겨 둔다.
- **언제**: 로그인 직후, 기기에서 바꾼 뒤 2초, 1분마다, "지금 동기화".

규약은 `supabase/README.md`에 있다.

## 서버

Supabase(PostgreSQL)다. 기기는 테이블을 직접 고치지 못하고(읽기 정책만 있다) 동기화 함수 두 개만 부른다. 가입하면 트리거가 가계부 · 프로필 · 기본 분류 · 현금 자산을 만든다.

## 빌드와 배포

푸시할 때마다 CI가 돈다(`.github/workflows/ci.yml`).

| 작업 | 내용 |
| --- | --- |
| 분석 · 시험 · 라이선스 | 형식, 분석, 시험, 생성 코드 확인, 의존성 라이선스 검사 |
| 서버 SQL | PostgreSQL 16에서 마이그레이션과 시험 |
| 웹 빌드 → 웹 배포 | `main`이면 GitHub Pages로 배포 |
| Android APK, Windows | 빌드해 Artifacts로 올린다 |

의존성과 모델은 소스 공개 의무가 없는 허용형 라이선스만 쓴다.
